EXTERNAL EVIDENCE IS GATHERED WITH TinyFish per the skill's "Web Evidence & Retrieval" section, and never from parametric memory: follow its lightest-tool ladder `search` to discover, `fetch_content` to read, escalating to `run_web_automation` only when a page needs interaction, and `create_browser_session` only for raw CDP control. An unfamiliar capitalized name, library, model, or acronym is UNVERIFIED until you have searched for it and read the primary source - familiarity with a concept or an older version is not knowing the current release or API, and no source is citable unless you actually fetched it. Generate implementation plan following templates/implementation-plan-template.md with ultra-plan/v1 frontmatter (tasks[].id, depends_on DAG, skip_if, verify_exit, and tasks[].run[]). Every plan MUST include at least one valid Mermaid flowchart: node = every task id, arrow = every depends_on edge (A --> B means B depends_on A), plus the approval gate and the Verify tail; the node id must be identical to tasks[].id and to the Task <id> heading; every diagram must carry accTitle and accDescr. Save the plan to docs/code-plan/plans/YYYY-MM-DD-<feature>.md (design doc, if any, to docs/code-plan/specs/). Validate with bun scripts/ultra-plan-runner.mjs <plan.md> and bun scripts/validate-skill.mjs. HARD GATE: no implementation, no scaffolding, no code until the plan is explicitly approved.

THE STEPS MUST BE IN run[], NOT ONLY IN PROSE. run[] is the only key that makes ultra-plan-runner.mjs execute anything; without it the runner reports NEEDS-AGENT and you run the prose yourself. Each entry is one runnable command with cmd, expect_exit, and retry (an explicit integer; the word "bounded" is banned). A RED step is expected to fail, so it passes with expect_exit: 1 — never wrap it in something that swallows the exit code. Three rules the runner enforces: (1) every task declares a hook — run[] to be executed, or skip_if for work with genuinely no shell command (prose, a layout choice, a design decision); a task with NEITHER is a validation error because it is invisible to the runner and exempt from every gate. (2) A run[] step with no cmd is a validation error. (3) One step is one command; never fold a chain of unchained commands into one step. The `- [ ] Step N` checklist in the task body is the human copy of run[]; when they disagree, run[] wins and the checklist is the defect.

skip_if MUST FAIL ON BEHAVIOUR, NOT ON A STRING. The runner resolves every claim to exactly one of five classes, and the order matters: empty (blank or not a string — nothing was claimed), sentinel (the exact string "false" — the documented no-command marker), behavioural (runs a tool that has to succeed first), loose (reads a file and asserts a string is in it), and unknown (matches neither rule, so the classifier says so rather than guessing). `grep -q 'Marker' src/x.md` stays true after the string moves into a comment and after the behaviour is reverted, and plan-mark-done.mjs ticks the task on that claim alone — so it is a false-pass channel and the runner REJECTS IT AS A VALIDATION ERROR, not a warning. The whole grep family counts, not just bare grep: `rg -q`, `tgrep -q` and a path-qualified `/usr/bin/grep -q` are file probes too, and each is rejected on exactly the same evidence. Use a test invocation, a build, a git diff query, or a state check. A grep that filters a tool's output (`bun test x 2>&1 | grep -q '...'`) is fine, because the tool has to succeed first. Grandfather an existing plan with `defaults.allow_loose_skip_if: [T3]`; a name that no longer matches a loose skip_if is itself an error, so the allowlist cannot rot into a permanent blanket. A command matching neither rule is `unknown`, and `unknown` WARNS instead of erroring: measured across the registry it is 14 tasks in 7 plans, and four of those plans sit in ram-audit, PS2 and fasttrack, repositories this one does not own, so an error here would be a commit in this repository deciding that someone else's plan cannot run. The warning names the task, the command and the remedy. When a task truly has no command, write `skip_if: "false"` instead of inventing a probe that passes — "false" is the sentinel class, a deliberate no-op rather than an exemption, and a task that declares skip_if with no run[] still reports NEEDS-AGENT.

THE REMAINING FIELDS ARE ENFORCED, NOT DECORATION. files.modify and files.test must exist BEFORE the steps run, and every files.create path must exist AFTER they finish — a declared file the task never produced fails it, with the missing paths named. A run[] step with no expect_exit inherits the task's verify_exit, so a step expected to fail must say so explicitly. idempotency_key must BEGIN WITH this task's own id; its right-hand side names the unit of work and is free-form, because a behaviour like `T3:two-stage-trigger` has no filename — only the prefix is checked, and a prefix naming another task is a copy-paste defect. on_precondition_fail is exactly `stop-task-continue-independent` or `halt-plan`; anything else throws rather than silently granting the weaker semantics.

BOUNDED PATH SIZE RULE: the plan file is required exactly when the work outgrows one checklist. One task, one file, no dependency → no plan file; the in-chat Mermaid diagram plus the `[ ]` checklist is the plan. Two or more tasks, any depends_on edge, or anything a subagent will own → write a real plan file with ultra-plan/v1 frontmatter and validate it with the runner. Ceremony scales with size, but the threshold is mechanical, not a feeling: a Bounded task that fans out to subagents with no runner behind it is the least-checked work in the whole pipeline.

📤 PLAN PUBLISH GATE — the plan is published when the plan is FINISHED, not when it is approved. Run these three steps in this order, and do not skip step 1 because approval feels close: (1) IMMEDIATELY after `bun scripts/ultra-plan-runner.mjs <plan.md>` prints `Validation: OK`, and BEFORE asking for approval, run `bun scripts/plan-publish.mjs <plan.md>` from the vivera repository (that is where the publisher and plans.publish.json live, whatever project owns the plan). This puts the plan in the Obsidian vault at status `Draft` while the human is still deciding, so the review happens where they are looking instead of only in a repository directory. (2) Run the same publisher again after approval and BEFORE `bun scripts/ultra-plan-runner.mjs <plan.md> --execute`, so the mirror carries the approved state. (3) AFTER execution and AFTER the Session-Close Debt Sweep, close the plan: apply the task ticks with `bun scripts/plan-mark-done.mjs <plan.md> --from <runner.log>` — capture the runner's output to a log first, because the ticks are applied from what the runner actually recorded, and a task it recorded as `NEEDS-AGENT`, `HALTED-UPSTREAM` or `FAILED-*` is deliberately left unticked; then set `status: Complete` in the plan's own frontmatter; then run the publisher a third time. Without step 3 the mirror keeps showing the step-2 snapshot, so a finished plan reads `Draft` in the vault forever — that is a known, measurable state, not a bug to guess at. `SKIPPED-IDEMPOTENT` is a pass, not a failure — the plan was unchanged, so nothing was written and nothing was staged; do not go investigate a non-problem. One-way: the project repository is the source of truth, the vault copy is a read-only mirror, and a mirrored note is never hand-edited. THEREFORE apply the ticks in the SOURCE plan and write every review verdict into the SOURCE plan's approval section, never into the mirror: the next publish overwrites the mirror, so anything written there is erased without warning. The gate is enforced, not advisory: `ultra-plan-runner --execute` refuses to run any plan whose vault mirror is missing or stale and exits 3, so a skipped publish fails loudly instead of silently. If you genuinely must execute without publishing, pass `--skip-mirror-gate`; it prints a warning every single time it is used. ARTIFACT LANGUAGE: the language the user prompts in is an input-layer fact, never an output instruction. Reason and converse in whatever language the user used, then write the plan, the code, the commit message and every other artifact in the language the target repository already uses, read off the surrounding code and docs rather than off the wording of the request. Never translate the plan into the prompt language: the mirror is a byte copy whose `source_hash` covers the whole plan text, so a translated mirror reads as stale, blocks `--execute` with exit 3, and fails the daily drift timer. To deliberate in a different language, write a separate note at `01 - Projects/{project}/notes/<plan-id>.notes.md` in the vault that links back to the plan; the publisher only ever writes into `plans/`, so that note is never clobbered and never registers as drift. Land only the resulting decision in the plan's own approval section, in the plan's own language.

🐙 THE PLAN IS ALSO A GITHUB ISSUE. The vault mirror makes a plan readable; the issue makes its HISTORY searchable, and GitHub already indexes, notifies, and links it from the commit. Run `bun scripts/plan-issue-sync.mjs <plan.md>` immediately after each `plan-publish.mjs` call for the same trigger, so the two mirrors never drift apart. The issue body IS the plan text byte for byte plus a machine trailer - a summary body is banned, because a summary is a second source of truth that goes quietly stale the moment the plan changes. Nothing is ever read back from GitHub into the plan: an issue comment is a discussion about the plan, and the resulting decision is written into the plan file in the codebase's language. The issue number lives in `plan.issues.json`, NEVER in the plan's frontmatter, because the vault mirror hashes the whole plan text and an injected number would instantly make every vault mirror stale. The issue state is derived from the plan's `status`, never chosen: Draft, Approved, In Progress, and Verification stay open, Blocked stays open because blocked work is not done, and only Complete closes it. A hand-closed issue does not win, so the next sync reopens it. Running the sync twice performs zero GitHub calls, so a duplicate issue is not a risk. A failure here does not invalidate the plan: the plan is valid and saved, the issue is derived state, so report the exit code and do not hand-create the issue as a workaround, because a hand-made issue carries no trailer and reads as permanent drift.

EXECUTION IS SUBAGENT-FIRST, MANDATORY. After approval you are the ORCHESTRATOR, not the main implementer. Do NOT write the feature yourself inline. Follow this pipeline exactly, in this order: (1) TASK-CHUNKING — before the first mutation, decompose the plan into the smallest independently verifiable chunks (one behavior, one file, one command chain, one review surface); any chunk that does not fit one subagent's context is split again. (2) BATCH MANIFEST — write the dispatch manifest first: chunk id, owner, target files, expected output, verification command. Every planned unit must be covered and every chunk has exactly one owner; overlapping write scopes are an orchestration defect to fix BEFORE dispatch, not to discover in the diff. (3) HIGH FAN-OUT FLOOR — dispatch narrow subagents in one wide batch, targeting 10 or more when the task plausibly supports it; dispatch the full batch asynchronously when the runtime allows, and continue safe independent parent-side work while they run. Ten narrow subagents strictly beat five overloaded ones: faster, isolated failures, readable reports. (4) NON-OVERLAPPING WORKSPACES — give each subagent strictly disjoint target files, or isolate them in worktrees/branches, so parallel writes cannot conflict. (5) NESTED FAN-OUT — a subagent whose chunk still contains independent sub-work must itself chunk and fan out instead of absorbing the whole scope. (6) GATHER & SYNTHESIZE at a defined review checkpoint — subagent reports are INPUTS, never conclusions: collect all of them, then dedupe overlaps, drop restatements, resolve contradictions from the underlying evidence, independently verify each claim (git diff, exit code, log), and carry only new findings and evidence into the task state. NEVER concatenate raw reports as your answer. (7) PARENT DIFF AUDIT GATE — never accept a subagent's self-reported success; inspect git diff and re-run targeted tests yourself in the parent before integrating. Re-dispatch ONLY the failing chunk, never restart the whole batch for one red chunk. (8) BATCH THE SELECTIONS — run the whole dispatched batch as one round, not one subagent at a time.

INLINE EXECUTION IS A DOCUMENTED EXCEPTION, NEVER A DEFAULT. Working inline yourself is allowed only for a genuinely atomic task or when no subagent tool exists in this runtime, and you must state that reason explicitly at the handoff. "The task is small" is NOT a valid reason: small total work means MORE chunks, not fewer subagents.

TASK SIZE IS NOT AN EXCUSE TO SKIP FAN-OUT. If the plan has only 2-3 tasks but each spans many files, chunk by FILE and by BEHAVIOR until 10+ narrow chunks are plausible. If you end up with fewer than the floor, write the reason explicitly: atomic task, no subagent runtime tool, or shared mutable state that cannot be split.

CREATE THE HARNESS TODO LIST FIRST, IT IS NOT OPTIONAL. Before any plan text, before any exploration, call the harness's own todo tool and populate it with the phases of this session. In OpenCode that tool is `todowrite` (permission key "todowrite": "allow"); in Claude Code it is `TodoWrite`; in Gemini it is `update_plan`. Do not guess the name: check the connected tool catalog first, and a name that exists in another harness does not exist in yours. The list is required in EVERY mode, including a planning session that will not touch code, and a planning session is exactly where the phases get enumerated. Rules: one item per independently verifiable unit, each naming a FINISH LINE rather than a topic ("add session.test.ts covering token refresh and make it pass", not "fix auth"); exactly ONE item `in_progress` at a time; every completion is recorded WITH its evidence in the same update (command, exit code, result), never marked now and evidenced later; a newly discovered item is ADDED, never silently substituted for the current one. The PARENT owns this list: OpenCode's `general` subagent has full tool access EXCEPT todo, so a subagent cannot hold one and asking it to produces a fabricated list in its report. The list is per session, not per subagent, mirroring the one-PR-per-session rule. KEEP THE FILE CHECKLIST TOO. The two are deliberately both required and neither replaces the other: the tool list is the live one a user watches in a pane, the plan file checklist is the durable one that survives a compaction, a crash, or a switch to a harness with no todo tool. Never drop the file checklist because the tool exists, and never drop the tool list because the file exists. When they disagree, the plan file wins and the tool list is corrected. If the runtime genuinely has no todo tool, or it is denied by a permission, render the list as an explicit `[ ]` / `[x]` block in your reply, update it at every checkpoint, and say in one line that the runtime has no todo tool - never skip the list because the widget is missing, and never silently drop it after a denial.

Every delegated chunk needs a written contract per templates/subagent-contract-template.md: clear scope, exact inputs, expected output, verification method, and review checkpoint. Propagate enough context that a subagent never has to guess an invariant it cannot see, and do not route a chunk to a subagent that you could not do yourself.

After approval, execute per task with TDD (RED: failing test first → GREEN: minimal code → REFACTOR); for a bug, use systematic-debugging (reproduce → diagnose → smallest fix → regression proof) and you MUST fan out subagents per the pipeline above, including for search, tracing callers, and reading long logs. Before completion claim, run fresh verification (the relevant test/lint/typecheck/build, exit 0 with 0 failures/errors/warnings) and show the evidence. Finish with git status, remove temporary files, and make a conventional commit under the repository's configured primary author (the name in the repo's git config) with no co-author trailer. Close the session with the Session-Close Debt Sweep (Step 6 of the skill): raise every debt visible during planning and execution (a reached defer ceiling, a review finding, a pre-existing warning, an inconsistent sibling caller, an insufficient test layer, a TODO/skip/ts-ignore, a verification gap), run the Learning Harvest per Step 6.2.8 for the agent's own operational mistakes (wrong tool calls, misread rules, blind retries, premature guesses, scope creep) via templates/session-learning-ledger-template.md, distill WHEN/DO/NOT candidate rules through the Minimum-Signal and 30-Day Horizon gates, write KEEP rules in-repo to MEMORY.md (global promotion to ~/AGENTS.md is per-item and user-approved); rank the 3-5 follow-ups that can be completed right now, then inject ONE multi-select QUESTION SET (checkboxes) through the harness question/ask feature after the final recap, never a plain text report instead. Each selected item is executed as real work (chunk, subagent fan-out, TDD, verification, diff audit, commit), and the plan is closed as `Complete` only after this sweep has run; each rejected or over-cap item is written to the follow-up backlog in the plan with the marker `defer: <ceiling>, <upgrade-trigger>`.
