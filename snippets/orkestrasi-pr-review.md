# Snippet Orkestrasi: PR Review Standalone

> Copy-paste the block below into the agent chat when you want a pull request
> somebody else opened reviewed against the full evidence gate. By default this
> is review-only; it merges to main only when the same request explicitly
> pre-authorizes auto-merge AND every gate in AUTO-MERGE below passes.
>
> This block is a **trigger prompt**: the agent reads it as an instruction, not a
> summary. The REVIEW-ONLY DEFAULT, POSTING-GATE, and AUTO-MERGE rules below are mandatory.
>

> copied. Copy a single PR URL for one PR, or several (one per line) for a batch.

Load `sucp-rules` and `sucp-verify-deliver` (section 5.4, Reviewing a PR) by name before the review starts; if the skill tool cannot load them, read `~/vivera/skills/<name>/SKILL.md` and say so.

TARGET RESOLUTION RUNS FIRST, BEFORE ANY REVIEW WORK. The text below `#{clipboard}` was substituted at expansion time and is the ONLY statement of what to review. Resolve it to an ordered list of `(owner/repo, number)` pairs, then work that list. Do not ask the user to restate a target the text already names.

Accepted shapes, and nothing else is a target:
- One full URL: `https://github.com/owner/repo/pull/123`
- One `#123`, or `owner/repo#123`, when the repo is unambiguous from the remote of the current checkout
- Several of the above, one per line or separated by whitespace or commas (the multi-PR case)
- A bare URL fragment the clipboard mangled: reconstruct it only when owner, repo, and number are all present after reconstruction, and state the reconstruction in one line
- An empty or whitespace-only value, or a value containing no recognizable target at all: STOP and say exactly what was received and what shape was expected. Never guess a nearby PR number, never review whatever `gh pr list` happens to show first, and never fall back to the branch you are standing on. An unresolved target is a stop with the received value quoted, not an invitation to improvise.

Echo the resolved list back before reviewing: each pair, whether it is `main`-targeted, and whether it is already merged or closed. For a single PR, say `1 PR: owner/repo#123`. For a batch, say `N PRs: ...` with the numbers in the order you will review them. Deduplicate: the same PR listed twice is reviewed once. Two targets in DIFFERENT repositories is a stop and a question, not two reviews in two clones, because one review verdict per repository is the unit of judgement here.

WORK SCOPE. Work ONLY on the REVIEW of the resolved pull request(s), following the review path of "Pull Request Delivery, Review & Batch Merge" in sucp-verify-deliver. The default deliverable is the review report file, not code. Do not implement a fix, do not push, do not open a new PR. Merge ONLY through the AUTO-MERGE section below, never as a default.

BATCH BEHAVIOUR IS NOT A REPEAT WITH A BIGGER NUMBER. A single PR takes the whole pipeline below once. A batch of N (including N=10 and beyond) takes it once PER PR, with these three rules added:
1. **One verdict per PR, never one verdict for the batch.** A PR is `correct` or `not correct` on its own evidence. The batch summary reports the per-PR verdicts side by side and derives no batch-level verdict, because three correct PRs and one incorrect one do not average into anything.
2. **Fan-out scales with the batch, chunk boundaries do not.** Chunk each PR independently by coverage category and dispatch across the whole batch, one owner per (PR, category) pair. Never let two subagents touch the same PR-and-category cell, and never let one subagent span two PRs.
3. **Merges stay strictly sequential even when reviews were parallel.** Reviews parallelize; merges do not. After each individual merge, `git fetch origin main`, then re-verify, then take the next PR. Twenty reviews followed by twenty back-to-back merges without a check in between is the batch failure this rule exists to prevent. When one PR cannot be made mergeable it is marked and skipped; the rest of the batch continues.

EVIDENCE IS GATHERED WITH TinyFish per the "Web Evidence & Retrieval" section of sucp-brainstorm whenever the review depends on external library, RFC, or upstream-issue facts: `search` to discover, `fetch_content` to read, escalating to `run_web_automation` only when a page needs interaction. An unfamiliar capitalized name, library, or acronym in the diff is UNVERIFIED until you searched and read the primary source. Cite source plus date.

KEEP THE TO-DO LIST IN THE PLAN FILE. Before any exploration, plan text, or review text, write the phases of this session as an itemized `[ ]` checklist in the plan file, one item per independently verifiable unit, each naming a finish line rather than a topic. Do not use the harness's own todo tool: the list lives in the planning document only. Check an item `[x]` only in the same update that cites its evidence (command, exit code, result). A newly discovered item is added, never silently substituted for the current one. The parent owns this checklist; subagents return reports and never maintain one.

REVIEW IS SUBAGENT-FIRST, MANDATORY. For anything beyond a trivially small diff, you are the ORCHESTRATOR of the review, not its only reader. Do NOT read the whole diff, trace every caller, and check every category yourself inline. Use this pipeline: (1) TASK-CHUNKING - split the review into the smallest independently verifiable units, one per coverage category or risk surface: functionality, test reversal, scope, security, compatibility, data and migration, observability, documentation, artifacts. (2) BATCH MANIFEST - before dispatch write the manifest: chunk id, category under test, files or commands in scope, expected output (a verdict per category: pass / finding with evidence), and the verification command. Every coverage category must be covered and every chunk must have exactly one owner. (3) HIGH FAN-OUT FLOOR - dispatch narrow reviewer subagents in one wide batch, targeting as many parallel checkers as the diff plausibly supports. (4) NON-OVERLAPPING SCOPES - give each subagent a disjoint category or file set. Two subagents must never claim the same finding location. (5) NESTED FAN-OUT - a subagent whose chunk still contains independent risk surfaces must itself chunk and fan out rather than absorb the whole review. (6) GATHER & SYNTHESIZE at a defined review checkpoint - subagent reports are INPUTS, never conclusions: collect all of them, then dedupe overlaps, drop restatements, resolve contradictions from the underlying evidence, independently verify each claim (diff line, command output, fetched source), and carry only new confirmed findings forward. NEVER concatenate raw reports as your answer. (7) PARENT DIFF AUDIT GATE - never accept a subagent's "looks good" on trust; inspect `gh pr diff <n>` yourself in the parent before writing the verdict. Write a per-chunk contract per templates/subagent-contract-template.md: scope, exact inputs, expected output, verification method, review checkpoint.

FETCH AND RECORD EVERY INPUT FIRST. For each resolved PR, run `gh pr view <n> --json number,title,author,baseRefName,headRefName,commits,reviews`, `gh pr diff <n>`, `gh pr view <n> --json commits`, existing review comments, prior verdicts, and `gh pr checks <n>`, and record each in section 2 of templates/pr-review-template.md. Pass `--repo <owner/repo>` on every `gh` call whenever the resolved repo differs from the checkout's remote, so a mixed or non-local target cannot silently read the wrong repository. A row marked "not consulted" with a reason is honest; a blank row is indistinguishable from a checked-and-clean row and reads as the latter. Remote CI status is reported as the author's evidence and is never adopted as your own verification.

ANSWER EVERY COVERAGE CATEGORY per templates/pr-review-template.md section 3 (functionality, test reversal, scope, security, compatibility, data and migration, observability, documentation, artifacts) with `N/A` plus a reason where one applies. State the test-reversal check explicitly: which test would go red if the change were reverted. If none would, that is a finding, not a neutral observation.

QUALIFY EVERY FINDING against all 8 criteria in templates/code-review-template.md section 3 - do not duplicate that template here, use it as the shared filter. Anchor each finding to a line the diff actually touched on the correct side (a comment on an unchanged line either fails to post or degrades into a general remark pretending to be specific), tag it P0-P3 with a numeric confidence 0.0-1.0, and report every qualifying finding rather than the first one. Pre-existing debt is reported separately with a `defer:` marker, never filed as a finding.

THE VERDICT IS BINARY AND DERIVED. Write section 6 of templates/pr-review-template.md with exactly `correct` or `not correct`: `not correct` if and only if at least one P0/P1 finding exists, never a hedge. Name the specific checkable condition that would change it, because "after the author addresses comments" is not a condition. For a batch, one report file per PR plus one index listing every PR with its verdict, its blocking findings count, and whether it merged; the per-PR reports are the record and the index is a table of contents, never a substitute.

FINDINGS THAT SPAN PRs ARE NOT MERGED INTO ONE. When two PRs in the batch touch the same interface, the same file, or the same contract, review each on its own diff and say so explicitly in both reports, naming the counterpart PR. Do not write one finding that spans both, because a comment anchored to a line only one of them touched cannot be posted to the other. A cross-PR concern becomes a note in each affected report plus, when it needs its own PR, a follow-up line in the backlog.

GENERATING A REVIEW AND POSTING IT ARE TWO ACTS. The posted comment is a shorter artifact than the internal report: verdict, blocking findings, and nothing else. Internal reasoning, discarded candidates, and praise stay in the report. Nothing is posted or merged until a human has read the exact text that will be posted, EXCEPT when the triggering request pre-authorized auto-merge and every AUTO-MERGE gate below passes - that pre-authorization is the human gate, given in advance for the safe case only. The verdict posted or merged on is the one the evidence derived, never preference. A reviewer that posts or merges its own draft without pre-authorization has skipped the only gate this stage has. In a batch, pre-authorization covers every PR in the resolved list individually and never the batch as a unit: a human who said "review and merge if safe" authorized the safe ones, and authorizing the first merge does not authorize the second. When one PR fails a gate, the rest of the batch keeps its own authorization and continues.

AUTO-MERGE IS OPT-IN AND GATED, NEVER DEFAULT. Merge to main only when the triggering request explicitly pre-authorized it (for example "review and merge if safe") AND all of these hold: (1) verdict is `correct` with zero P0/P1 findings; (2) `gh pr checks <n>` shows all required checks green, plus your own `gh pr view <n> --json mergeable,mergeStateStatus,reviewDecision` shows mergeable with no blocking review decision; (3) base is `main`, with no unresolved review threads and no merge conflicts; (4) if the PR belongs to a pr-registry session, `bun scripts/pr-registry.mjs surface <session>` shows nothing blocking it. If ANY gate fails, stop after saving the report - a failed gate is a status, not a reason to force anything. Merge procedure, PARENT-ONLY and never delegated to a subagent: `git fetch origin main`, then `gh pr merge <n>` with the repository default method, never `--admin`, never `--force`, never bypassing branch protection EXCEPT under the single-maintainer condition stated below, never merging on a subagent self-report or on remote CI alone. After merging, record the merge evidence (command, exit code, resulting commit) in the report file and, if registry-tracked, record the state transition.

ERROR HANDLING IS EXPLICIT, NEVER IMPROVISED. Run `gh auth status` first; if auth fails, stop and report it - never work around a missing token. A PR number that does not exist, or a repo that does not match, is a stop with the exact command and stderr quoted, not a guess at a nearby number. In a batch, that stop applies to THE OFFENDING PR ONLY: record it as `not reviewed: <reason>` in the index, keep the other targets moving, and never let one unreachable PR cancel nine reviewable ones. Two failures repeat themselves: if two attempts at the same PR fail the same way, that PR is a status and the batch moves on without a third attempt. Pending checks count as a failed gate: stop and report which check is pending; do not poll in a loop and do not merge while anything is yellow. If `git fetch origin main` fails, stop - a merge on a stale base is unverified. Order of visible acts: post the review comment first, then merge; if posting fails, stop before merging, because a merge without a recorded verdict is unattributable. If `gh pr merge <n>` fails, quote the exit code and stderr, retry at most once and only for a transient transport error (a network timeout), never for a conflict. A protection or review-decision refusal is the SINGLE-MAINTAINER CASE and has its own rule: run the four measurements below before touching `--admin`, and treat a refusal as unmergeable when any measurement says the review was supposed to exist. An already-merged or closed PR is terminal: record the merge commit (or record closed state via `bun scripts/pr-registry.mjs state <session> closed` if tracked in pr-registry) and stop, do not error and do not touch anything. If the merge succeeded but a bookkeeping step (registry state, report write) failed, record the discrepancy in the report - never revert or un-merge to "fix" bookkeeping, because `merged` is terminal and a revert is a NEW change, not an undo.
 
THE ADMIN'S OWN APPROVAL ALWAYS PASSES, AND `--admin` IS THE ONE DOCUMENTED EXCEPTION. GitHub refuses self-approval outright (`Review Can not approve your own pull request`), so in a repository whose only collaborator is the admin and whose only CODEOWNER is that same admin, `required_approving_review_count: 1` can never be satisfied by anybody and a plain `gh pr merge <n>` is refused with "the base branch policy prohibits the merge". That is a dead gate, not a review, and waiting for an approver who does not exist is not an option. So for THAT repository shape the admin's own verification IS the approval, and `gh pr merge <n> --admin` is permitted. Four measurements decide it, and all four must hold: (1) `gh api repos/<o>/<r>/collaborators --jq length` returns exactly 1, and that one login is the authenticated actor; (2) the authenticated actor is the repository admin (`gh api user`, then compare against the single collaborator); (3) `gh pr view <n> --json reviewDecision` shows the ONLY blocking reason is `REVIEW_REQUIRED` with no `CHANGES_REQUESTED` and no unresolved threads; (4) the user explicitly pre-authorized this merge in the current request. If measurement 1 returns 2 or more, or measurement 3 shows a change request or an unresolved thread, then a real reviewer exists and `--admin` is FORBIDDEN: stop and report the refusal. `--admin` never excuses a `CHANGES_REQUESTED`, a red check, a conflict, a stale base, or a blocking finding, and it never applies to a repository that has any second collaborator. `--force` and pushing over a branch that already has a PR remain forbidden without exception. Measure before merging: this rule was written because a session hit the dead gate and could not tell an unsatisfiable requirement from a real review, then reported the wrong thing.

CLOSE WITH EVIDENCE, NOT PRAISE. Save the review report in .md format following templates/pr-review-template.md, with the internal diff notes kept per templates/code-review-template.md. Record commands with exit codes, including the merge evidence when AUTO-MERGE ran. Make sure to remember this skill while we are working in this session. Feel free to re-call this skill in every checkpoint. 📇 END-OF-SESSION GRAPH INDEX: the review report and notes must not stay invisible to `graphify query`/`path`/`explain`. The order is load-bearing. Verify with `bun run graphify:check` (exit 1 = stale) and preview with `--dry-run`. If graphify or `graphify-out/graph.json` is absent, record that in one line and move on.
