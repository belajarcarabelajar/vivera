# Snippet Orkestrasi: PR Delivery + Batch Merge

> Copy-paste the block below into the agent chat when you want a finished session
> turned into a pull request, twenty open PRs merged in a safe order, or a PR
> somebody else opened reviewed against the full evidence gate.
>
> This block is a **trigger prompt**: the agent reads it as an instruction, not a
> summary. The ISOLATION and PR-TERMINAL rules below are mandatory.

---

Apply super-ultra-code-plan (fallback chain: ~/vivera/Super Ultra Code Plan Implementation.md, then ~/.agents/skills/super-ultra-code-plan/SKILL.md, then ~/.gemini/config/skills/super-ultra-code-plan/SKILL.md, then ~/.config/opencode/skills/super-ultra-code-plan/SKILL.md, then ~/.claude/skills/super-ultra-code-plan/SKILL.md, then ~/.config/ai/Super Ultra Code Plan Implementation.md; use the first file found and state which path was used). Load `sucp-rules`, `sucp-verify-deliver` (PR delivery and batch merge), and `sucp-debt-sweep` by name before closing; if the skill tool cannot load them, read `~/vivera/skills/<name>/SKILL.md` and say so. Work on the session's PULL REQUEST, following the "Pull Request Delivery, Review & Batch Merge" section of sucp-verify-deliver. EVIDENCE IS GATHERED WITH TinyFish per the "Web Evidence & Retrieval" section of sucp-brainstorm whenever the review depends on external library, RFC, or upstream-issue facts: `search` to discover, `fetch_content` to read, escalating to `run_web_automation` only when a page needs interaction. An unfamiliar capitalized name, library, or acronym in the diff is UNVERIFIED until you searched and read the primary source. Cite source plus date.

ISOLATION IS DERIVED, NOT CHOSEN. Run `bun scripts/pr-registry.mjs claim --plan <plan-id> --session <session-slug> [--repo <root>] [--depends-on <slug>,<slug>]` and use the branch and worktree it PRINTS. A hand-written branch name is the exact defect this rule exists to stop: twenty panes naming their own branches produce two sessions on one ref, and the second push silently rewrites the first session's PR. Then, in the repository, BEFORE anything is written: `git worktree prune`, `git fetch origin main`, `git worktree add <printed-path> -b <printed-branch> origin/main`. The worktree sits BESIDE the repository, never inside it - a nested worktree is picked up by the parent's watchers, formatters, and test globs, which then operate on two copies of the same file. Subagents write ONLY inside that worktree. The claim is idempotent: a retried claim after a crashed session returns the same slot rather than allocating a second one.

GIT WRITES ARE PARENT-ONLY, MANDATORY. A subagent edits files and runs tests. It never runs `git commit`, `git add`, `git checkout`, `git switch`, `git merge`, `git rebase`, `git stash`, `git reset`, `git push`, or `gh`. The reason is mechanical, not stylistic: the git index is shared mutable state with no per-writer lock, so two subagents staging at once produce a commit containing a half-applied change from the other, and that commit was never tested in that shape. A subagent that says "I committed so it would be safe" has violated this; the deliverable is the tested file state, not the commit, so `git reset --soft HEAD~1` and keep the changes. When you integrate a chunk, read `git diff -- <permitted paths>`, confirm only those paths moved, and stage by EXPLICIT PATH - never `git add .`, which is what makes the PARENT DIFF AUDIT GATE mechanical instead of a review of whatever happened to be in the tree.

EXECUTION IS SUBAGENT-FIRST, MANDATORY. Any remaining implementation is chunked and fanned out: (1) TASK-CHUNKING into the smallest independently verifiable units before the first mutation; (2) BATCH MANIFEST written before dispatch with chunk id, owner, target files, expected output, verification command, every chunk exactly one owner and no two chunks writing the same file; (3) HIGH FAN-OUT FLOOR targeting 10 or more narrow subagents when the task plausibly supports it, dispatched as one wide async batch; (4) NON-OVERLAPPING WORKSPACES, which here means all of them inside the one session worktree on disjoint files; (5) NESTED FAN-OUT for a chunk that still contains independent sub-work; (6) GATHER & SYNTHESIZE at a defined review checkpoint, where reports are INPUTS and never conclusions - dedupe, drop restatements, resolve contradictions from the underlying evidence, verify each claim independently via diff and exit code, and carry only new findings forward; (7) PARENT DIFF AUDIT GATE, re-running the targeted tests yourself in the parent before integrating. A red chunk is re-chunked and re-dispatched ALONE, never by restarting the batch, and never twice unchanged. Inline work is a documented exception with a stated reason, never a default. Write a per-chunk contract per templates/subagent-contract-template.md.

VERIFY LOCALLY, THEN OPEN THE PR. Before the PR: run the relevant test, lint, typecheck, and build commands on the machine holding the working tree and show exit codes with 0 failures, 0 errors, 0 warnings. A hosted runner cannot see your tree, your vault, or your database, so a green remote run is the author's evidence about a commit, not your verification - and you never push in order to make someone else's runner check your work. Then follow templates/pull-request-template.md exactly, write the body to a FILE, and post with `gh pr create --base main --head <branch> --title "<imperative title>" --body-file <path>` - never `--body`, because multi-line markdown with backticks, newlines, and checkboxes is error-prone on a command line. The body is written in the CODEBASE's language, not the language the request arrived in, since a translated PR body breaks grep for the next reviewer. No em dash in the body, the commit messages, or any user-visible string in the diff. Acceptance criteria map to a check and to evidence; "tests pass" is not evidence, the command and its exit code are. Commit under the repository's configured author with no co-author trailer, never directly to the base branch - there is no direct-to-main exception, and a one-line fix is simply a small session with its own branch. Then record it: `bun scripts/pr-registry.mjs pr <session> --number <N>`. A PR that exists but is unregistered is invisible to the merge order, so it never lands.

SESSION STATES ARE A GATE, NOT A LABEL. `isolated -> active -> verified -> open -> merged | closed`. Record each transition with `bun scripts/pr-registry.mjs state <session> <state>`. A PR number cannot be recorded before `verified`, because recording one implies the work is finished and checked. Only an `open` session with a PR can merge - a green local run alone is not mergeable. Both `merged` and `closed` are terminal: `closed` is for a PR closed without merging (satisfies dependencies without moving the base branch; `surface` never lists it as landed), and reverting or redoing a session is a NEW session with a new branch, never a state edit, because a file that can "un-merge" hides the revert from the merge order. Do not hand-edit pr.registry.json to reach a state; the tool refuses unknown states, unknown commands, and duplicate branches or worktrees rather than falling back to a default.

BATCH MERGE IS SEQUENTIAL AND ORDER-COMPUTED. Run `bun scripts/pr-registry.mjs order` for the merge order and `bun scripts/pr-registry.mjs surface <session>` for what must rebase first. The order is TOPOLOGICAL from the recorded `depends_on` graph, never chronological, with ties broken on session name so the same registry always produces the same order - a timestamp tiebreak would make the printed plan unreproducible. Already-merged sessions drop out and stop blocking their dependents, so a session waiting on nothing still lands. A dependency cycle is refused with the cycle named; the remedy is to split a session, not to pick an arbitrary order. Then, ONE AT A TIME: rebase that session's branch onto `origin/main` immediately before its own merge, because the base moves with every merge and a branch rebased at position 3 is already behind by position 7; resolve any conflict IN THE SESSION BRANCH, never on the base branch, since editing main to "fix" a conflict produces a change no session can attribute or review; re-run that session's verification after resolving; merge this one PR; re-run the local check on the new base as the evidence FOR THAT MERGE. Never batch twenty merges and test at the end: that leaves nineteen merges unverified. A session that cannot be made mergeable is reported and skipped while the rest of the batch proceeds; it is a status, not a reason to freeze nineteen others. Never force-merge to clear a queue, never force-push a branch that already has a PR, and never merge on the strength of a green remote CI run or a subagent's self-report.

REVIEWING A PR FOLLOWS A SEPARATE CONTRACT. When asked to review a PR rather than to deliver one, follow templates/pr-review-template.md, and the internal diff review stays in templates/code-review-template.md - do not duplicate one into the other. Fetch and RECORD every input first: `gh pr view <n> --json ...`, `gh pr diff <n>`, commits, existing review comments, prior verdicts, `gh pr checks <n>`. A row marked "not consulted" with a reason is honest; a blank row is indistinguishable from a checked-and-clean row and reads as the latter. Remote CI status is reported as the author's evidence and is never adopted as your own verification. Answer every coverage category (functionality, test reversal, scope, security, compatibility, data and migration, observability, documentation, artifacts) with `N/A` plus a reason where one applies, and state the test-reversal check explicitly: which test would go red if the change were reverted. If none would, that is a finding, not a neutral observation. A finding passes all 8 qualification criteria in templates/code-review-template.md, is anchored to a line the diff actually touched on the correct side (a comment on an unchanged line either fails to post or degrades into a general remark pretending to be specific), is tagged P0-P3 with a numeric confidence, and every qualifying finding is reported rather than the first one. The verdict is binary and derived: `not correct` if and only if at least one P0/P1 finding exists, never a hedge, and it names the specific checkable condition that would change it because "after the author addresses comments" is not a condition.

KEEP THE TO-DO LIST IN THE PLAN FILE. Before any exploration, plan text, or review text, write the phases of this session as an itemized `[ ]` checklist in the plan file, one item per independently verifiable unit, each naming a finish line rather than a topic. Do not use the harness's own todo tool: the list lives in the planning document only. Check an item `[x]` only in the same update that cites its evidence (command, exit code, result). A newly discovered item is added, never silently substituted for the current one. The parent owns this checklist; subagents return reports and never maintain one.

GENERATING A REVIEW AND POSTING IT ARE TWO ACTS. The posted comment is a shorter artifact than the internal report: verdict, blocking findings, and nothing else. Internal reasoning, discarded candidates, and praise stay in the report - praise in a posted review reads as filler and the repository's own copy rules ban it in user-visible text. Nothing is posted until a human has read the exact text that will be posted, and the verdict posted is the one the human chose, not the one the reviewer preferred. A reviewer that posts its own draft has skipped the only gate this stage has.

CLOSE THE ISSUE LAST, AFTER THE SWEEP. The debt sweep is what finally sets the plan to `status: Complete`, and the plan's GitHub issue state is derived from that status, so the issue is still open while the sweep runs and closes only after it. When the plan is `Complete` and the sweep is done, run `bun scripts/plan-issue-sync.mjs <plan.md>` one final time so the issue closes with the plan rather than staying open on finished work. Do not close the issue by hand: a hand-closed issue does not win over the plan, and the next sync reopens it, so a manual close is undone silently. The same sync also refreshes the body after the follow-up commits land, because the issue body IS the plan text and every commit changes it.

CLOSE THE SESSION WITH THE DEBT SWEEP. After the PR is open, close with the Session-Close Debt Sweep (Step 6, sucp-debt-sweep): raise every debt visible during the session (a reached `defer:` ceiling, a review finding, a pre-existing warning, an inconsistent sibling caller, an insufficient test layer, a TODO/skip/ts-ignore, a verification gap), run the Learning Harvest per Step 6.2.8 for operational mistakes via templates/session-learning-ledger-template.md, distill WHEN/DO/NOT candidate rules through the Minimum-Signal and 30-Day Horizon gates, write KEEP rules in-repo to MEMORY.md (global promotion to ~/AGENTS.md is per-item and user-approved); rank the 3-5 follow-ups that can be completed right now, then inject ONE multi-select QUESTION SET (checkboxes) through the harness question/ask feature after the final recap, never a plain text report instead. Each selected item is executed as real work on the SAME session branch - chunk, subagent fan-out, TDD, verification, diff audit, commit, push - and pushes into the same open PR, so a follow-up never needs a second PR. Each rejected or over-cap item is written to the follow-up backlog in the plan with the marker `defer: <ceiling>, <upgrade-trigger>`. Make sure to remember this skill while we are working in this session. Feel free to re-call this skill in every checkpoint. Always save the PR body, the review report, the learning ledger, and the merge evidence in .md format. 📇 END-OF-SESSION GRAPH INDEX: those Markdown artifacts must not stay invisible to `graphify query`/`path`/`explain`. In the session's repository run `graphify update .` first (code graph), then run `bun run graphify:sync` from the vivera repository (the pipeline it reuses lives there) to union the documents' structural chunk nodes into that repository's `graphify-out/graph.json`. The order is load-bearing, because `update` rewrites the graph and can discard document nodes added before it. The sync is local (no LLM call, no API key, no network), deterministic and idempotent: it remaps graphify-era document ids rather than duplicating them and retains every code/concept/rationale node. Verify with `bun run graphify:check` (exit 1 = stale), preview with `--dry-run`, and if graphify or `graphify-out/graph.json` is absent it refuses rather than fabricating a graph — record that in one line and move on.
