# Snippet Orkestrasi: PR Review Standalone

> Copy-paste the block below into the agent chat when you want a pull request
> somebody else opened reviewed against the full evidence gate. By default this
> is review-only; it merges to main only when the same request explicitly
> pre-authorizes auto-merge AND every gate in AUTO-MERGE below passes.
>
> This block is a **trigger prompt**: the agent reads it as an instruction, not a
> summary. The REVIEW-ONLY DEFAULT, POSTING-GATE, and AUTO-MERGE rules below are mandatory.

---

Apply super-ultra-code-plan (fallback chain: ~/ai-skills/Super Ultra Code Plan Implementation.md, then ~/.agents/skills/super-ultra-code-plan/SKILL.md, then ~/.gemini/config/skills/super-ultra-code-plan/SKILL.md, then ~/.config/opencode/skills/super-ultra-code-plan/SKILL.md, then ~/.claude/skills/super-ultra-code-plan/SKILL.md, then ~/.config/ai/Super Ultra Code Plan Implementation.md; use the first file found and state which path was used). Work ONLY on the REVIEW of pull request <n> in <owner/repo>, following the skill's "Pull Request Delivery, Review & Batch Merge" review path. The default deliverable is the review report file, not code. Do not implement a fix, do not push, do not open a new PR. Merge ONLY through the AUTO-MERGE section below, never as a default.

EVIDENCE IS GATHERED WITH TinyFish per the skill's "Web Evidence & Retrieval" section whenever the review depends on external library, RFC, or upstream-issue facts: `search` to discover, `fetch_content` to read, escalating to `run_web_automation` only when a page needs interaction. An unfamiliar capitalized name, library, or acronym in the diff is UNVERIFIED until you searched and read the primary source. Cite source plus date.

CREATE THE HARNESS TODO LIST FIRST, IT IS NOT OPTIONAL. Before any review text, call the harness's own todo tool and populate it with the phases of this review. In OpenCode that tool is `todowrite` (permission key "todowrite": "allow"); in Claude Code it is `TodoWrite`; in Gemini it is `update_plan`. Do not guess the name: check the connected tool catalog first. Rules: one item per independently verifiable unit, each naming a FINISH LINE rather than a topic ("fetch diff plus checks for owner/repo#n and record inputs", not "review PR"); exactly ONE item `in_progress` at a time; every completion is recorded WITH its evidence in the same update (command, exit code, result). The PARENT owns this list: never delegate it to a subagent. If the runtime genuinely has no todo tool, render the list as an explicit `[ ]` / `[x]` block in your reply and say so in one line.

REVIEW IS SUBAGENT-FIRST, MANDATORY. For anything beyond a trivially small diff, you are the ORCHESTRATOR of the review, not its only reader. Do NOT read the whole diff, trace every caller, and check every category yourself inline. Use this pipeline: (1) TASK-CHUNKING - split the review into the smallest independently verifiable units, one per coverage category or risk surface: functionality, test reversal, scope, security, compatibility, data and migration, observability, documentation, artifacts. (2) BATCH MANIFEST - before dispatch write the manifest: chunk id, category under test, files or commands in scope, expected output (a verdict per category: pass / finding with evidence), and the verification command. Every coverage category must be covered and every chunk must have exactly one owner. (3) HIGH FAN-OUT FLOOR - dispatch narrow reviewer subagents in one wide batch, targeting as many parallel checkers as the diff plausibly supports. (4) NON-OVERLAPPING SCOPES - give each subagent a disjoint category or file set. Two subagents must never claim the same finding location. (5) NESTED FAN-OUT - a subagent whose chunk still contains independent risk surfaces must itself chunk and fan out rather than absorb the whole review. (6) GATHER & SYNTHESIZE at a defined review checkpoint - subagent reports are INPUTS, never conclusions: collect all of them, then dedupe overlaps, drop restatements, resolve contradictions from the underlying evidence, independently verify each claim (diff line, command output, fetched source), and carry only new confirmed findings forward. NEVER concatenate raw reports as your answer. (7) PARENT DIFF AUDIT GATE - never accept a subagent's "looks good" on trust; inspect `gh pr diff <n>` yourself in the parent before writing the verdict. Write a per-chunk contract per templates/subagent-contract-template.md: scope, exact inputs, expected output, verification method, review checkpoint.

FETCH AND RECORD EVERY INPUT FIRST. Run `gh pr view <n> --json number,title,author,baseRefName,headRefName,commits,reviews`, `gh pr diff <n>`, `gh pr view <n> --json commits`, existing review comments, prior verdicts, and `gh pr checks <n>`, and record each in section 2 of templates/pr-review-template.md. A row marked "not consulted" with a reason is honest; a blank row is indistinguishable from a checked-and-clean row and reads as the latter. Remote CI status is reported as the author's evidence and is never adopted as your own verification.

ANSWER EVERY COVERAGE CATEGORY per templates/pr-review-template.md section 3 (functionality, test reversal, scope, security, compatibility, data and migration, observability, documentation, artifacts) with `N/A` plus a reason where one applies. State the test-reversal check explicitly: which test would go red if the change were reverted. If none would, that is a finding, not a neutral observation.

QUALIFY EVERY FINDING against all 8 criteria in templates/code-review-template.md section 3 - do not duplicate that template here, use it as the shared filter. Anchor each finding to a line the diff actually touched on the correct side (a comment on an unchanged line either fails to post or degrades into a general remark pretending to be specific), tag it P0-P3 with a numeric confidence 0.0-1.0, and report every qualifying finding rather than the first one. Pre-existing debt is reported separately with a `defer:` marker, never filed as a finding.

THE VERDICT IS BINARY AND DERIVED. Write section 6 of templates/pr-review-template.md with exactly `correct` or `not correct`: `not correct` if and only if at least one P0/P1 finding exists, never a hedge. Name the specific checkable condition that would change it, because "after the author addresses comments" is not a condition.

GENERATING A REVIEW AND POSTING IT ARE TWO ACTS. The posted comment is a shorter artifact than the internal report: verdict, blocking findings, and nothing else. Internal reasoning, discarded candidates, and praise stay in the report. Nothing is posted or merged until a human has read the exact text that will be posted, EXCEPT when the triggering request pre-authorized auto-merge and every AUTO-MERGE gate below passes - that pre-authorization is the human gate, given in advance for the safe case only. The verdict posted or merged on is the one the evidence derived, never preference. A reviewer that posts or merges its own draft without pre-authorization has skipped the only gate this stage has.

AUTO-MERGE IS OPT-IN AND GATED, NEVER DEFAULT. Merge to main only when the triggering request explicitly pre-authorized it (for example "review and merge if safe") AND all of these hold: (1) verdict is `correct` with zero P0/P1 findings; (2) `gh pr checks <n>` shows all required checks green, plus your own `gh pr view <n> --json mergeable,mergeStateStatus,reviewDecision` shows mergeable with no blocking review decision; (3) base is `main`, with no unresolved review threads and no merge conflicts; (4) if the PR belongs to a pr-registry session, `bun scripts/pr-registry.mjs surface <session>` shows nothing blocking it. If ANY gate fails, stop after saving the report - a failed gate is a status, not a reason to force anything. Merge procedure, PARENT-ONLY and never delegated to a subagent: `git fetch origin main`, then `gh pr merge <n>` with the repository default method, never `--admin`, never `--force`, never bypassing branch protection, never merging on a subagent self-report or on remote CI alone. After merging, record the merge evidence (command, exit code, resulting commit) in the report file and, if registry-tracked, record the state transition.

ERROR HANDLING IS EXPLICIT, NEVER IMPROVISED. Run `gh auth status` first; if auth fails, stop and report it - never work around a missing token. A PR number that does not exist, or a repo that does not match, is a stop with the exact command and stderr quoted, not a guess at a nearby number. Pending checks count as a failed gate: stop and report which check is pending; do not poll in a loop and do not merge while anything is yellow. If `git fetch origin main` fails, stop - a merge on a stale base is unverified. Order of visible acts: post the review comment first, then merge; if posting fails, stop before merging, because a merge without a recorded verdict is unattributable. If `gh pr merge <n>` fails, quote the exit code and stderr, never retry with `--admin` or `--force`, retry at most once and only for a transient transport error (a network timeout), never for a protection, conflict, or review-decision refusal. An already-merged or closed PR is terminal: record the merge commit (or record closed state via `bun scripts/pr-registry.mjs state <session> closed` if tracked in pr-registry) and stop, do not error and do not touch anything. If the merge succeeded but a bookkeeping step (registry state, report write) failed, record the discrepancy in the report - never revert or un-merge to "fix" bookkeeping, because `merged` is terminal and a revert is a NEW change, not an undo.
 
CLOSE WITH EVIDENCE, NOT PRAISE. Save the review report in .md format following templates/pr-review-template.md, with the internal diff notes kept per templates/code-review-template.md. Record commands with exit codes, including the merge evidence when AUTO-MERGE ran. Make sure to remember this skill while we are working in this session. Feel free to re-call this skill in every checkpoint. 📇 END-OF-SESSION GRAPH INDEX: the review report and notes must not stay invisible to `graphify query`/`path`/`explain`. After saving them, in the session's repository run `graphify update .` first (if code changed), then run `bun run graphify:sync` from the vivera repository (the pipeline it reuses lives there) to union document structural chunk nodes into `graphify-out/graph.json`. The order is load-bearing. Verify with `bun run graphify:check` (exit 1 = stale) and preview with `--dry-run`. If graphify or `graphify-out/graph.json` is absent, record that in one line and move on.
