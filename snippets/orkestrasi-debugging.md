EXTERNAL EVIDENCE IS GATHERED WITH TinyFish per the "Web Evidence & Retrieval" section of sucp-brainstorm, and never from parametric memory: follow its lightest-tool ladder `search` to discover, `fetch_content` to read, escalating to `run_web_automation` only when a page needs interaction, and `create_browser_session` only for raw CDP control. An unfamiliar capitalized name, library, model, or acronym in a stack trace or an upstream issue is UNVERIFIED until you have searched for it and read the primary source - a half-remembered API shape is a candidate hypothesis to test, not a fact to build a fix on, and no source is citable unless you actually fetched it. Cite source plus date. Diagnose root cause (violated invariant + why), document the full RCA in .md log following templates/systematic-debugging-log-template.md including its Mermaid debugging-loop diagram (accTitle and accDescr are mandatory). Track investigation state in templates/progress-log-template.md. HARD GATE: await explicit approval of the RCA before patching; no code without approval gate.

INVESTIGATION IS SUBAGENT-FIRST, MANDATORY. For anything beyond a single obvious one-file cause, you are the ORCHESTRATOR of the investigation, not its only worker. Do NOT trace the whole call stack, read every call site, and grep every log yourself inline. Use this pipeline: (1) TASK-CHUNKING — split the investigation into the smallest independently verifiable units, one per hypothesis: one candidate root cause, one caller chain, one log slice, one failing-test variant, one config/source-of-truth surface. Chunk by HYPOTHESIS, not by file, so parallel work tests competing explanations in parallel instead of serially. (2) BATCH MANIFEST — before dispatch write the manifest: chunk id, hypothesis under test, files or commands in scope, expected output (a verdict: confirmed / disproven / inconclusive with evidence), and the verification command. Every candidate cause must be covered and every chunk must have exactly one owner; overlapping write scopes are an orchestration defect to fix BEFORE dispatch. (3) HIGH FAN-OUT FLOOR — dispatch narrow subagents in one wide batch and target 10 or more when the investigation plausibly supports it. A wide bug surface, a regression touching many callers, or an intermittent failure with many candidate causes all fan out wide. Async-dispatch the full batch when the runtime allows and keep doing safe independent parent-side work meanwhile. Ten narrow investigators strictly beat one overloaded investigator: hypotheses get tested in parallel, a disproven cause is discarded without contaminating the others, and each report stays readable. (4) NON-OVERLAPPING SCOPES — give each subagent a disjoint file set, log slice, or hypothesis. Two subagents must never edit or claim the same file. Isolate in worktrees or branches when read-write overlap is unavoidable. (5) NESTED FAN-OUT — a subagent whose chunk still contains independent candidate causes must itself chunk and fan out rather than absorb the whole search. (6) GATHER & SYNTHESIZE at a defined review checkpoint — subagent reports are INPUTS, never conclusions: collect all of them, then dedupe overlapping findings, drop restatements, resolve contradictions from the underlying evidence (a diff, an exit code, a log line), independently verify each surviving claim yourself, and carry only confirmed findings into the RCA. NEVER concatenate raw reports as the diagnosis. (7) PARENT DIFF AUDIT GATE — never accept a subagent's "root cause found" or "fixed" claim on trust; inspect git diff and re-run the repro yourself in the parent before accepting it. Re-dispatch ONLY the failing or disproven chunk; never restart the whole batch for one red chunk. (8) BATCH THE INVESTIGATION — run the dispatched batch as one round, not one investigator at a time.

INLINE INVESTIGATION IS A DOCUMENTED EXCEPTION, NEVER A DEFAULT. Investigating inline yourself is allowed only when the cause is genuinely atomic and obvious (a single stack trace with an unambiguous line, a typo, a missing import) or when no subagent tool exists in this runtime, and you must state that reason explicitly. "The stack trace is short" is NOT a valid reason: a short trace with several plausible causes is exactly the case that fans out best. SHOTGUN DEBUGGING IS PROHIBITED — no speculative parallel edits, no changing code to see what happens, and no fixing symptoms before the root cause is isolated with a reproducing failing test.

🐙 THE PLAN IS ALSO A GITHUB ISSUE. The vault mirror makes a plan readable; the issue makes its HISTORY searchable, and GitHub already indexes, notifies, and links it from the commit. Run `bun scripts/plan-issue-sync.mjs <plan.md>` immediately after each `plan-publish.mjs` call for the same trigger, so the two mirrors never drift apart. The issue body IS the plan text byte for byte plus a machine trailer - a summary body is banned, because a summary is a second source of truth that goes quietly stale the moment the plan changes. Nothing is ever read back from GitHub into the plan: an issue comment is a discussion about the plan, and the resulting decision is written into the plan file in the codebase's language. The issue number lives in `plan.issues.json`, NEVER in the plan's frontmatter, because the vault mirror hashes the whole plan text and an injected number would instantly make every vault mirror stale. The issue state is derived from the plan's `status`, never chosen: Draft, Approved, In Progress, and Verification stay open, Blocked stays open because blocked work is not done, and only Complete closes it. A hand-closed issue does not win, so the next sync reopens it. Running the sync twice performs zero GitHub calls, so a duplicate issue is not a risk. A failure here does not invalidate the plan: the plan is valid and saved, the issue is derived state, so report the exit code and do not hand-create the issue as a workaround, because a hand-made issue carries no trailer and reads as permanent drift.

FIX VERIFICATION IS ALSO FAN-OUT. After the patch, dispatch subagents to independently re-run the repro test, re-run the neighboring regression suite, audit every sibling caller of the changed function for breakage, and review the diff for the 8 qualification criteria per templates/code-review-template.md. These are independent checks and belong in one batch, not in one sequential pass.

KEEP THE TO-DO LIST IN THE PLAN FILE. Before any exploration, plan text, or review text, write the phases of this session as an itemized `[ ]` checklist in the plan file, one item per independently verifiable unit, each naming a finish line rather than a topic. Do not use the harness's own todo tool: the list lives in the planning document only. Check an item `[x]` only in the same update that cites its evidence (command, exit code, result). A newly discovered item is added, never silently substituted for the current one. The parent owns this checklist; subagents return reports and never maintain one.

MUST write a per-chunk contract per templates/subagent-contract-template.md: scope, exact inputs, expected output, verification method, review checkpoint. Propagate enough context that an investigator never guesses an invariant it cannot see, and never route a chunk to a subagent you could not do yourself. Apply smallest safe localized fix (no unrelated refactor) after the RCA approval gate, classify the failure (code/test/contract/environment/infrastructure/pre-existing) in the Error Ledger, then verify: repro test GREEN plus targeted regression suite with 0 failures, fresh evidence shown. Close the session with the Session-Close Debt Sweep (Step 6, sucp-debt-sweep): raise every debt from this investigation (code that is still hardcoded, a sibling caller that was never touched, a test that is still flaky, a pre-existing warning, a Root Cause that was never removed systematically, a documentation gap), run the Learning Harvest per Step 6.2.8 for operational mistakes via templates/session-learning-ledger-template.md, distill WHEN/DO/NOT candidate rules through the Minimum-Signal and 30-Day Horizon gates, write KEEP rules in-repo to MEMORY.md (global promotion to ~/AGENTS.md is per-item and user-approved); rank the 3-5 follow-ups that can be completed right now, then inject ONE multi-select QUESTION SET (checkboxes) through the harness question/ask feature after the final recap, never a plain text report instead. Each selected item is executed through the full pipeline (chunk, subagent fan-out, TDD, verification, diff audit, commit); each rejected or over-cap item is written to the follow-up backlog with the marker `defer: <ceiling>, <upgrade-trigger>`. Make sure to remember this skill while we are working in this session. Feel free to re-call this skill in every checkpoint. Always save result of investigation, learning ledger, and fix in .md format. 📇 END-OF-SESSION GRAPH INDEX: the debugging log, fix report, progress log, and learning ledger you just wrote must not stay invisible to `graphify query`/`path`/`explain`. PROGRESS METER: whatever this trigger asks for, open every message to me in the chat that reports progress (a checkpoint, a phase change, a status or recap, the final report) with one meter line, as `sucp-rules` Progress Meter at Checkpoints defines it: `▰▰▰▱▱▱▱▱▱▱ 30% · 3/10 · <item in progress>`.
